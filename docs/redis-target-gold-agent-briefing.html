03 / RESOURCE FLOW REPAIR

用 ResourceEvent 和四步传播把资源生命周期连起来

事件：acquire / release / transfer / borrow / escape / invalidate 字段：resource_id、resource_type、expression、function、thread、file/line、condition、owner、evidence_ids

1. 资源实体识别

把 uv__make_pipe(pipefd)、scandir(..., &dents, ...)、req->addrinfo、req->ptr 提升为资源实体，并把 req 作为拥有字段的父对象。

2. 别名和字段传播

建立 pipefd[1] -> loop->async_wfd、dents -> req->ptr、req->addrinfo -> callback 参数，别名图必须跨函数保留。

3. 宏和 transfer 识别

结合 02-macro/macros.json 与源码行，把 POST 展开为资源提交；将 uv_fs_open -> uv__work_submit 识别为所有权转移，后续 release 允许发生在另一函数。

4. 路径选择

同一资源在 uv__async_start 可能有 uv__open_cloexec 和 uv__make_pipe 两条平台分支；uv__fs_scandir_cleanup 的多个 release 也要按 condition 保留，不能只取第一个或最后一个。

已验证结果：libuv resource_flow 达到 17 TP / 0 FP / 0 FN，evidence_hit_rate = 100%。核心不是多记一个枚举，而是保留 owner、alias、condition 和 evidence。

Gold 中的重点机制

  • 队列发布、程序顺序和事件通知。
  • 条件变量、锁和 thread join。
  • atomic release/acquire 与 unknown。
  • rwlock 和允许并发但不能建立 HB。

需要补齐的同步模型

  • 同步事件：mutex、cond、atomic、join、poll、callback。
  • 线程身份和 create/join 关系。
  • 同一 mutex、condition、queue item、atomic 实例。
  • held_locks、reads-from、batch 和成功条件。
  • happens-before / concurrent / unknown 三值判定。
修复规则：队列 unlock -> 下次 lock 建立 HB；cond wait 会释放并重获 mutex； join 后建立 HB；seq_cst atomic 可建立 release/acquire； relaxed、合并通知和失败 trylock 输出 unknown； rwlock writer -> reader/writer 可建立 HB，reader-reader 为 concurrent。

sync_006 的根因是锁和计数递减已识别，但中间 if 占用了旧规则的唯一后继。现在“锁获取到释放之间的首个受保护写”可独立建边，134 -> 137 已命中。100% 仅覆盖冻结 Gold，不覆盖 2,950 条未标注输出。
