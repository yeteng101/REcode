## 实际执行流程

```text
固定 base/head → 第一组 HTTP 分析 → 公共层准备 → Reviewer
Reviewer → Test Worker → 宿主审查及冻结 → 健康/原缺陷各三次执行
复现验收 → Patch Worker → Git 捕获差异 → Docker 构建与行为回归
修复验收 → 修复源码独立快照 → 第一组重新提取 → 最终证据审计
```

宿主根据保存的 `next_action` 创建模型角色。stdio MCP 提供提交和边界推进接口，编排器持久化每个动作及状态。确定性步骤通过 `advance_lock_race_run_until_boundary` 连续执行，到下一个模型任务时停下。

第一组提供对象声明、访问、线程创建/join 和锁状态事实。公共层准备影响范围、源码及证据，Concurrency 确定性代码形成候选。注册的 `lock_race_reviewer` 逐例复核对象身份、并发关系、共同保护和 PR 关联。

Test Worker 在产品修复开始前编写测试。宿主审查实际断言和调度，冻结文件并执行健康对照及原缺陷版本。原缺陷三次均命中目标行为断言后，编排器才创建隔离产品 worktree。

注册的 `lock_race_patch_worker` 修改指定源码，宿主通过 Git 获取实际差异。Docker 编译、smoke 和冻结行为回归全部通过，且前后差异哈希一致时，最终记录为 `verified`。

修复后的重新提取使用独立 clone 和仅供验证的提交，逐文件核对其内容与已验证 worktree 一致。原始仓库及补丁工作树继续保留。

## 测试实际检查的行为

两份测试都调用实际 `writer_a`、`writer_b`、`observe` 和资源辅助源码。源码中的两个更新分别贡献 `+2` 与 `+1`，观察函数再加一。

### 一侧缺锁

测试作者生成两个持久线程，每批各调用真实回调 4096 次。三个参与者的开始及完成 barrier 保证宿主读取时两个更新线程处于静止状态。每批完成后断言 `counter = 3 × 4096 × 批次数`，并检查真实 `observe(counter)` 为该结果加一。

原缺陷三次均在第一批触发断言。预期 counter 为 12288，实际分别为 12044、12064、12234。

### 两侧持不同锁

测试作者生成两个持久线程，分 128 批各调用真实回调 2097152 次。两个参与者的 barrier 对齐每批起止，主线程等待两个工作线程结束后检查真实观察结果为 6291457。

原缺陷三次实际结果分别为 5428949、5449294、5773741，均触发退出码 42。

两个断言都基于完成后的算术行为。测试元数据标记中立协议 `behavior`。产品互斥锁的初始化及生命周期保持源码语义，测试自身拥有 barrier。

这种验证采用有界并发压力，操作系统决定具体读写交错。当前记录证明连续三次复现以及修复后三次通过，穷尽调度证明状态为 `not_run`。设置、API 或超时失败采用退出码 90，单独分类为测试装置问题。
