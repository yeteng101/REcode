# REcode 跨函数字段绑定

- 基线 `sync-field-binding` 的 `ac35748`，继承本地 `group3` 的 `e52eedd`。
- 工作分支 `sync-cross-function-binding`。
- 状态 直接调用实现和验收完成，2026-11-24。

## 目标

把已确认的函数内部字段访问沿直接调用边绑定到调用方的实参。先支持接收者指针原样转发、单定义局部指针复制和具名对象取地址。原生 JSON 保留调用点、实参来源、参数序号及字段访问的证据。具名全局对象沿调用边保留字段对象 ID。对参数和自动局部存储保留对应作用域。 [局部字段绑定](sync-field-binding-2026-11-24.md)

分析以已解析到的直接调用和编译单元为范围。无法确定定义、弱符号或重定向符号、重写和逃逸的指针、指针算术和内存间接载入保留未知。调用链限制深度和输出量，只有链路中共享的确切来源可供绑定。已有 `shared_objects`、线程上下文和第三组契约保持原有含义。

跨函数事实从 `semantic_sync.field_bindings.direct_calls.bindings` 读取，证据 ID 与原有 `field_bindings.evidence` 同表。优先走当前编译单元中可用的定义。跨编译单元须有唯一可用的定义，存在多个编译版本时保持未知。链路以到达所解析调用为条件，最多 4 层、每条访问最多 16 条链、全输出最多 256 条链。函数仅支持由接收者指针派生字段地址的访问。

## 验收

1. 用真实 Clang 验证跨文件的两级调用、两个具名对象分别传参、参数或局部指针转发，以及重写、逃逸、间接调用和不明指针来源的反例。
2. 通过正式 CLI 检查原生证据及边界，跑现有语义同步、字段绑定和内存定向回归，并与基线比较全套测试。
3. 用 HPR-048 的固定提交静态验证 `uv__async_close` 到 `uv__async_spin` 的实参与字段访问。沿注册、入队和取出路径检查 `uv__async_io` 中 `h` 的证据。队列需要对象成员存取、跨调用副作用及容器地址恢复，如果直接调用规则无法证明链路，就记录能够证实的链路和第一个未知点。所有测试以通用规则为准。

## HPR-048 静态复测

固定 libuv 提交 `10902ab616058198067d6c2cc414014d36f86fff`，由 Clang 19.1.7 成功读取 70 个编译单元。`src/unix/async.c` 第 160 行调用 `uv__async_spin(handle)`，两条跨函数绑定分别关联该函数第 135 行和第 143 行的 `pending` 原子访问。两条均回溯到 `uv__async_close` 的第一个参数，接收者实际来自调用方，输出保留参数来源。

`src/unix/async.c` 的队列路径已核对到第 85 行入队、第 198 行转移队列、第 200 行取队头和第 201 行从成员恢复 `h`。直接传参规则在第 85 行已经到达边界。该调用把 `&handle->queue` 写入队列内部，字段子对象和存储关系超出了本轮的具名对象与直接转发。后续 `uv__async_io` 的 `h` 在原生输出中仍为局部指针来源，队列来源及其与 `uv_async_send` 实参之间的运行时对象关系仍未知。

HPR-048 共导出 2 条跨函数绑定，均为 `close → spin`，本次未触发输出上限。语义同步仍为 `partial`，已绑定执行上下文的共享对象仍为 0。第三组候选和端到端验证本轮未运行。
