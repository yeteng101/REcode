02 / BEFORE → AFTER

原来的分析能力已经跑通，但任务执行还停留在本地进程

之前

API 请求
→ ThreadPoolExecutor
→ 当前 Python 进程内执行
  • 任务队列和状态在内存中，进程退出后丢失。
  • 分析任务和 API 共用进程，长任务会拖住服务。
  • 任务不能可靠地跨进程恢复或继续消费。

现在

API → SQLite 任务账本
→ Worker 领取
→ 分析 / Trace / 上传
  • 任务状态、重试次数、租约和取消请求持久化。
  • API 和 Worker 可以分开启动、分别扩展。
  • 任务异常、重启和超时都有明确的恢复路径。

05 / FAILURE CASES

用明确的错误码和状态机替代“任务卡住”

Worker 被杀

租约到期 → 状态恢复为 queued → 新 Worker 重新领取；超过最大次数才进入 failed。

重复提交

相同幂等键和相同请求直接返回原 job_id，不重复启动分析。

临时故障

网络、对象上传、Worker 异常等可重试错误进入退避队列，不无脑重跑。

永久错误

源码不存在、参数错误、仓库超限、解析永久失败直接 failed，避免浪费资源。

用户取消

取消请求持久化；执行中的 Worker 协作退出，迟到结果不能覆盖 cancelled。

进程重启

任务和错误记录在数据库；重启后查询仍然存在，未完成任务由新 Worker 恢复。

06 / STORAGE CHOICE

选择 SQLite：先把单主机闭环做稳

SQLite 不是“缩小版生产环境”，而是一个边界清晰的单主机持久化方案。

适用

一台服务器；多个 API/Worker 进程；本地持久卷；内部试用和单团队分析服务。

可以支持

任务落库、租约恢复、幂等、重试、取消、清理和多进程 Worker。

不要误用

不要把数据库放到 NFS/SMB；不要用它假设多主机高可用。

未来升级

多主机时迁移 PostgreSQL + Redis/RabbitMQ/SQS，对象存储保持不变。

07 / SANDBOX SECURITY

不可信仓库不是“跑一下脚本”，而是多层边界的组合

01 / SOURCE
只接收公开 GitHub HTTPS 仓库，固定 commit 或受限分支；禁止本地路径、URL 凭证、重定向和任意主机。
02 / ARCHIVE
归档导入前检查路径穿越、符号链接、硬链接、设备和文件大小；跳过密钥、Agent 指令和 Gold 目录。
03 / CONTAINER
Docker 运行边界：无网络、无宿主挂载、只读根文件系统、非 root、无 capabilities、限 CPU/内存/磁盘/进程。
04 / BUILD
safe-generic 编译：不使用仓库自带 CMake、compile_commands、shell 或插件；编译参数由服务生成。
05 / OUTPUT
有界结果导出：分析结果通过限额 tar 传输，宿主机再次校验路径和文件类型。
08 / ISOLATION DETAILS

沙箱的重点是减少权限，而不是增加便利

容器层

  • 固定 image@sha256 digest，避免运行时漂移。
  • network=none；不挂载 Docker socket 或宿主密钥。
  • read-only rootfs；non-root；cap-drop ALL。
  • cgroups 限制 CPU、内存、swap、磁盘、pids 和文件数。
  • 超时、取消和结束都强制清理容器及其子进程。

数据层

  • 仓库归档先检查，再导入容器。
  • 不把宿主机目录直接挂进分析容器。
  • 结果只在分析结束后有界导出。
  • 对象存储与执行工作区分开。
  • 生产环境默认关闭本地仓库和旧宿主问答入口。

这一步不承诺“绝对安全”，目标是让仓库代码不能直接触达宿主网络、文件、密钥和其他用户数据。

09 / PROMPT INJECTION

最有效的防护不是提示词，而是让生产分析不依赖模型

生产链路默认执行 Clang 和静态分析工具，仓库里的 README、注释、日志无法改变执行权限。

防注入边界

  • 仓库内容全部视为不可信数据，不是指令。
  • 生产模式关闭宿主机 Agent 问答入口。
  • 源码读取路径限制在 repo root 内。
  • 不向容器暴露网络、密钥和评测 Gold。
  • 没有 evidence 的结论标记为 partial。

开发模式允许宿主机 Agent 时，提示词只是辅助防线，真正的安全边界仍是工具权限、沙箱和人工验收。
